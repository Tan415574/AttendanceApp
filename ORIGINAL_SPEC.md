## Prompt

Build a responsive website called **Present** for classroom attendance. It has two experiences: a **lecturer dashboard** and a **student-facing site**, sharing one backend/data store. No user accounts or passwords — identity is just a student number, and everything else is trust-based. Match a clean, soft health-app aesthetic: pastel green background, white rounded cards, soft shadows, circular progress rings, and simple bar/line charts.

### Core concept

The lecturer plans a weekly schedule of class sessions (lectures, workshops, tests, or custom types). Each real session gets opened on the day, which generates a short sign-in code and a QR code shown on the board. Students scan it on their phone, which opens the site straight to sign-in with the code pre-applied; if they've signed in before, they're checked in immediately, otherwise they enter their student number and name once. Students can view their own attendance score and a calendar (green = attended, red = missed, plain = no class), and can query a day they think is wrong. The lecturer gets stats/graphs and a queries inbox to resolve disputes.

### Roles

- **Lecturer**: builds the schedule, opens/closes sessions, views stats and graphs, manages the roster, resolves attendance queries.
- **Student (first time)**: scans code → enters student number → enters name (one-time) → checked in.
- **Student (returning)**: scans code → recognised by student number → checked in automatically.

### Features to build

**1. Schedule builder (lecturer)**
- Add sessions by day of week, start/end time, and type.
- Built-in types: Lecture, Workshop, Test. Lecturer can also add their own custom types.
- Support recurring weekly sessions and one-off sessions (e.g. a single test date, or cancelling one occurrence for a holiday).

**2. Live session (lecturer)**
- "Start" a scheduled session → generates a short code (5 characters, avoid ambiguous characters like 0/O, 1/I) and a QR code.
- QR encodes the sign-in page's own URL with the code attached as a query param, so scanning opens the site directly with the code applied.
- Show a live "X of Y students checked in" counter while the session is open.
- "Close" invalidates the code — no further check-ins accepted for that session.
- Allow a manual add for a student who couldn't scan.

**3. Sign-in (student)**
- Lands on the sign-in page, code pre-filled from the QR link (fallback: manual code entry).
- Invalid/expired code → clear message, path to re-enter a code.
- New student number → ask for full name once, save, then check in.
- Known student number → check in immediately, no extra fields.
- Already-checked-in-today state, in case of a duplicate scan.
- Confirmation screen: session type/time + success message.

**4. Student attendance page**
- Prominent overall attendance score (circular progress ring).
- Calendar view of the term: green ring = attended, red ring = missed, plain = no class scheduled that day.
- Tapping a day shows which session(s) were scheduled and their status.
- "Query this day" action available on any red (missed) day.

**5. Attendance queries (dispute flow)**
- Student: pick/confirm the date, add an optional note ("I was there, near the door"), submit. Shows as "Pending review" on their own calendar until resolved.
- Lecturer: queries inbox listing student, session, date, and note for every pending query. Approve (flips the day to present) or decline (stays absent), with an optional reply. Keep a resolved-queries history with who decided and when, for an audit trail.

**6. Stats & graphs (lecturer)**
- Attendance trend over time (line/bar chart, week by week).
- Breakdown by session type (Lecture vs Workshop vs Test vs custom types).
- Per-student table sortable by attendance %, with low-attendance students flagged.
- Drill into a single student to see their full session-by-session history.

**7. Roster management (lecturer)**
- View all registered students (student number + name).
- Manually add or remove a student (e.g. to fix a typo, or pre-load a class list).

### Data model

- **Students**: `studentNumber` (unique key, uppercase), `name`.
- **Scheduled sessions**: `id`, `type`, `date`, `startTime`, `endTime`, `status` (scheduled / open / closed), `code` (only meaningful while open).
- **Attendance records**: one row per student per session — `present: true/false`, `checkedInAt` timestamp.
- **Queries**: `studentNumber`, `sessionId`, `note`, `status` (pending / approved / declined), `resolvedBy`, `resolvedAt`.

Attendance score = (sessions marked present) ÷ (total scheduled sessions so far). Don't store this as a separate stat — derive it from the records so it can't drift out of sync.

### Design direction

- Palette: soft pastel green background, white cards with generous rounded corners (18–24px) and soft shadows, one confident accent green for primary actions and progress rings.
- Typography: a rounded/geometric sans for headings and numbers, a clean sans for body text.
- Signature visual: the circular attendance-score ring, echoed in both the student's score and the lecturer's per-session live counter.
- Keep the sign-in flow to as few taps as possible — it's used by an entire class, repeatedly, so speed matters more than decoration there.
- Mobile-first for the student-facing pages (sign-in, my attendance); the lecturer dashboard can assume a larger screen (laptop/projector) but should still be usable on a tablet.

### Explicit non-goals / known trade-offs

- No password or identity verification beyond the student number — anyone with the code can check in as any student number they type. This is intentional, optimising for speed and zero setup.
- No location/proximity verification that a student is physically present.
- No integration with an institution's official student records or SSO — that's a future step if attendance ever becomes high-stakes (e.g. tied to grades).

### Suggested build order

1. Schedule builder + data model for sessions/students.
2. Live session flow (start/close, code + QR, live counter) + student sign-in flow (new and returning).
3. Student attendance page: score + calendar.
4. Lecturer stats & graphs.
5. Queries: student submission + lecturer inbox + resolution history.
